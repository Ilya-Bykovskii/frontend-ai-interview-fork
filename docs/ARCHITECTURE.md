# Architecture and decisions

This file is the project's memory. The agent reads it at the start of every session, so decisions survive a cleared context.

## Architecture

Written by the agent from the candidate's description. What belongs here is described in `AGENTS.md`.

### Структура
- `src/api/` — типизированные функции запросов на `fetch` (без Redux). Базовый `http.ts` (BASE_URL, разбор `ApiError`, проброс `AbortSignal`) и `products.ts`.
- `src/entities/<entity>/` — типы сущности и RTK slice с thunks (`createAsyncThunk`) и селекторами. Сущности: `product` (`list`, `details`), `category`.
- `src/store/` — `configureStore`, типы `RootState`, `AppDispatch`.
- `src/hooks/` — абстрактные хуки (типизированные `useAppDispatch`/`useAppSelector`, debounce, работа с query-параметрами).
- `src/page/` — UI страницы на компонентах `@mui/material`: `index.tsx` (только композиция), `ProductFilters.tsx`, `ProductTable.tsx`, `ProductDetailsDialog.tsx`, `format.ts` (форматтеры и подписи). Каждый компонент сам читает URL-состояние через хук и свои данные из store.

### Поток данных
URL query (react-router `useSearchParams`) → страница читает и валидирует фильтры (`q`, `category`, `sortBy`, `order`, `productId`) → dispatch thunk → `api/` → `fetch` → slice хранит данные, `total` и статус загрузки → UI.
Изменение фильтров в UI пишет в URL (`push`/`replace` по решению 10), что запускает новый запрос. Фильтры в Redux не дублируются. Запрос отправляется только при изменении параметров; предыдущий запрос отменяется.

### Конвенции
Из `docs/requirements_1.md`–`docs/requirements_3.md`:
- Загрузка показывается явно; ошибка — с кнопкой повтора.
- Отсутствующие значения показываются как «—», а не пустота или `undefined`.
- Числа и деньги отформатированы и выровнены вправо, даты в читаемом виде.
- Длинные названия не ломают таблицу.

### Definition of done
- `npm run typecheck` и `npm run lint` проходят.
- Обязательные пункты текущего этапа `docs/requirements_<N>.md` выполнены.

## Decisions

Entries are added by the agent once the candidate confirms them. The format is described in `AGENTS.md`.

### 1. Стек и структура папок
- Context: таблица продуктов с серверной фильтрацией, пагинацией и состоянием в URL.
- Decision: RTK (`@reduxjs/toolkit`, `react-redux`), запросы через `fetch` + `createAsyncThunk`; слои `api/`, `entities/`, `store/`, `hooks/`, UI в `page/index.tsx`.
- Why: выбор кандидата; `store/` добавлен для конфигурации store и его типов.

### 2. Поиск и категория одновременно
- Context: API не позволяет совместить `/products/search` и `/products/category/:slug`.
- Decision: оба поля доступны; при непустом поиске категория игнорируется, в UI показывается подсказка.
- Why: сохраняет серверную пагинацию. Отклонены: взаимоисключающие фильтры, клиентская фильтрация категории.

### 3. URL — источник истины для фильтров и пагинации
- Context: параметры должны сохраняться в query.
- Decision: фильтры и пагинация читаются из URL; Redux хранит только данные и статус запроса. URL обновляется через `replace`. Синхронизация — `react-router` (`useSearchParams`).
- Why: нет двойного состояния и двусторонней синхронизации; `replace` не засоряет историю. Отклонены: slice фильтров с синхронизацией в URL, ручной `history` API.

### 4. Сортировка
- Context: API поддерживает `sortBy`/`order`.
- Decision: в этой итерации сортировку не делаем.
- Why: решение кандидата.

### 5. Объём этапа 1
- Context: `docs/requirements.md` описывает этап 1 без фильтров и пагинации.
- Decision: сначала этап 1 (таблица на 20 строк + модалка), фильтры, пагинация и query — следующим этапом.
- Why: решение кандидата; работа маленькими шагами.

### 6. Размер страницы
- Context: требования — «первые 20».
- Decision: всегда 20 на страницу, в query хранится только `page`.
- Why: решение кандидата; выбор размера страницы не требуется.

### 7. Открытый товар в URL
- Context: модалка с полным товаром.
- Decision: id открытого товара хранится в query (`?productId=12`); ссылка открывает модалку сразу. Закрытие удаляет параметр.
- Why: решение кандидата; согласуется с решением 3 (URL — источник истины).

### 8. Хранение краткого и полного товара
- Context: таблица запрашивает только свои колонки (`select`), модалка — полный товар по id.
- Decision: типы `ProductListItem` и `Product` в `entities/product/types.ts`; отдельные slices `productList` и `productDetails` со своими thunks и статусами.
- Why: кандидат попросил явно разделить разные типы объектов в типах и Redux. Отклонены: один slice с двумя ключами, две отдельные сущности.

### 9. Поиск вместе с категорией
- Context: требования этапа 3 — категория работает вместе с поиском и сортировкой; `/products/search` категорию игнорирует.
- Decision: при поиске с категорией запрашиваем `/products/search` с `limit=0` и сортировкой, фильтруем по категории на клиенте, показываем первые 20. Заменяет решение 2.
- Why: поиск и сортировка остаются серверными. Отклонены: клиентский поиск внутри категории, игнорирование категории.

### 10. История браузера
- Context: «Назад»/«Вперёд» должны переключать фильтры, набор текста не должен засорять историю.
- Decision: категория и сортировка — `push`; поиск — `push` на первую отправку в серии набора, далее `replace`. Серия — пока поле поиска в фокусе; сбрасывается при blur, смене другого фильтра, «Назад»/«Вперёд». `productId` и очистка невалидных значений — `replace`. Заменяет часть решения 3 про `replace`.
- Why: решение кандидата. Отклонены: `push` на каждую отправку поиска, поиск всегда через `replace`.

### 11. Сортировка
- Context: требования этапа 2.
- Decision: серверная сортировка по `title`, `price`, `discountPercentage`, `stock`, `rating`; цикл asc → desc → нет; одна активная сортировка; `sortBy`/`order` в URL. Заменяет решение 4.
- Why: требования этапа 2.

### 12. Пагинация
- Context: в требованиях 1–3 пагинации нет.
- Decision: не делаем, показываем первые 20 результатов текущих фильтров. Заменяет решение 6.
- Why: решение кандидата.

### 13. Язык и названия категорий
- Context: тексты в требованиях на русском; slug категорий нечитаем.
- Decision: весь интерфейс на русском, локаль форматирования `ru-RU`; slug выводится как «Home decoration» в селекте и в таблице.
- Why: решение кандидата.

### 14. Невалидные значения в URL
- Context: неизвестные значения не должны ломать приложение.
- Decision: неизвестные `category`, `sortBy`, `order`, `productId` считаются значением по умолчанию и удаляются из URL через `replace`; при наличии `category` в URL запрос товаров ждёт список категорий.
- Why: решение кандидата. Отклонено: игнорировать, не трогая URL.

### 15. Объём этапов 2–3
- Context: в требованиях есть обязательные и желательные пункты.
- Decision: обязательные и желательные пункты.
- Why: решение кандидата.

### 16. Разбиение UI страницы
- Context: `page/index.tsx` разрастается с добавлением поиска, категории и сортировки.
- Decision: файлы страницы в `src/page/` — `index.tsx` (композиция), `ProductFilters.tsx`, `ProductTable.tsx`, `ProductDetailsDialog.tsx`, `format.ts`. Компоненты независимы: сами читают URL-состояние через хук и свои данные из store, без проброса пропсов.
- Why: решение кандидата. Отклонены: слой `src/components/` для переиспользования, UI внутри `entities/`; передача данных пропсами со страницы.
