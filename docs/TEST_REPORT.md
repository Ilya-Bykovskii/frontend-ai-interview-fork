# Отчёт о тестировании

Дата проверки: 1 ноября 2026.

Проверялось текущее приложение каталога товаров против `docs/requirements_1.md`, `docs/requirements_2.md`, `docs/requirements_3.md` и зафиксированных решений в `docs/ARCHITECTURE.md`. Код по результатам проверки не менялся.

Проверка шла в браузере на `http://localhost:5173` против публичного API DummyJSON, плюс точечные запросы к API вне UI. `npm run typecheck` и `npm run lint` проходят.

## Как пользоваться отчётом

У каждой проблемы стабильный id. Он не переиспользуется. Исправление ищется по id, а не по заголовку.

| Префикс | Что это |
|---|---|
| `DEF-xxx` | Дефект поведения, найденный в UI или по однозначному пути в коде |
| `ARCH-xxx` | Архитектурное решение, которое стоит сменить или ограничить |
| `LIM-xxx` | Ограничение, принятое отдельным решением. Это не открытый дефект |
| `TC-xxx` | Проверка требования. Падение ссылается на `DEF` |

Статус в карточке: `open`, `fixed`, `accepted`. При исправлении меняется только карточка этого id: статус, дата и короткое примечание в поле «Исправление». Сводку вверху стоит обновить вместе со статусом.

Серьёзность дефектов: `major` — пользователь видит неверные данные или ломается сценарий; `minor` — заметно, обход есть или это частичное выполнение желательного пункта; `low` — в обычном UI не воспроизвелось, расходится с записанным решением.

Приоритет архитектуры: `now` — имеет смысл менять в текущей архитектуре; `later` — текущий экран не ломает, всплывёт при росте.

## Дефекты

### DEF-001

| | |
|---|---|
| Статус | fixed |
| Серьёзность | major |
| Область | модалка, кэш карточки |
| Требование | TC-104, пользователь должен видеть товар, который открыл |
| Связано | [ARCH-003](#arch-003) |
| Исправление | 1 ноября 2026. Карточки кэшируются по id; модалка читает запись открытого id, до ответа показывает «Товар» и спиннер. Уже в кадре `requestAnimationFrame` после клика прошлого товара нет |

**Симптом.** При открытии другого товара модалка сначала показывает предыдущий.

**Как проверено.** Был открыт Samsung Galaxy S8, SKU `SMA-SAM-SAM-132`. Следующий клик открыл Samsung Galaxy S10, в URL уже был `productId=133`. До кадра отрисовки и в `requestAnimationFrame` диалог всё ещё содержал заголовок S8 и SKU S8. Затем заголовок сменился на «Товар» и спиннер, после ответа — на S10.

**Причина.** Запрос стартует в эффекте, то есть после первой отрисовки. До эффекта диалог рисует `item` из store и не сравнивает его с `productId`. Закрытие модалки запись не очищает. `pending` обнуляет `item` только когда эффект уже выполнился.

**Где.** `src/page/ProductDetailsDialog.tsx`, выбор содержимого около строк 57–76. `src/entities/product/details/slice.ts`, `pending` около строк 28–31.

**Что сделать.** Рисовать карточку только при `item.id === productId`. Пока id не совпали, показывать спиннер. Модельное исправление — [ARCH-003](#arch-003): хранить карточку по id, а не одним слотом.

### DEF-002

| | |
|---|---|
| Статус | fixed |
| Серьёзность | major |
| Область | модалка, клавиатура |
| Требование | TC-109, желательный пункт этапа 1 |
| Связано | [DEF-008](#def-008) |
| Исправление | 1 ноября 2026. `disableRestoreFocus` у `Dialog`; после перехода закрытия (`onExited`) контейнер фокусирует кнопку в строке открытого товара. Проверено для Esc, фона и «Закрыть» |

**Симптом.** После закрытия модалки фокус оказывается на `body`, а не на строке, из которой её открыли.

**Как проверено.** Строка Samsung Galaxy S10 получала фокус, Enter открывал диалог. Esc закрывал его и убирал `productId`. Та же DOM-строка оставалась в таблице, `document.activeElement` был `body`. То же после закрытия мышью. Повтор с синтетическим Escape не закрывал диалог; проверялся настоящий Esc.

**Что при этом работает.** Enter и пробел открывают строку. У диалога есть `role="dialog"`, `aria-modal="true"` и `aria-labelledby`. Tab не выходит наружу и возвращается на «Закрыть». Закрытие кнопкой, фоном и Esc снимает `productId` через `replace`.

**Причина.** Возврат фокуса оставлен MUI. Ловушка фокуса запоминает `relatedTarget` события фокуса на самом диалоге. К этому моменту содержимое страницы уже под `aria-hidden`, браузер переносит фокус на `body`, и восстанавливать нечего.

**Где.** `src/page/ProductDetailsDialog.tsx`, `Dialog` без собственного восстановления фокуса. Строка — `src/page/ProductTable.tsx`, `TableRow` с `tabIndex={0}`.

**Что сделать.** Перед открытием запомнить строку. Когда `productId` становится `null`, вызвать у неё `focus()`. У диалога поставить `disableRestoreFocus`, чтобы MUI не перетирал это своим восстановлением.

### DEF-003

| | |
|---|---|
| Статус | fixed |
| Серьёзность | major |
| Область | фильтр категории |
| Требование | TC-301, TC-303 |
| Связано | [ARCH-006](#arch-006), [ARCH-007](#arch-007) |
| Исправление | 1 ноября 2026. Категория из URL добавляется в опции, пока список не загружен или упал; селект заблокирован только во время загрузки |

**Симптом.** Селект показывает «Все категории», хотя в URL уже есть категория. Пока список категорий не загружен или упал, селект ещё и выключен.

**Как проверено.** После загрузки ссылка `?category=smartphones&sortBy=price&order=asc` восстанавливается правильно: селект «Smartphones», 16 строк, один запрос категории. Промежуточное состояние в браузере поймать не удалось, список успевал прийти раньше замера. Несовпадение следует из кода и проявляется в двух местах.

1. Пока статус списка `idle` или `loading`, `items` пуст. Условие `items.includes(filters.category)` ложно, значение селекта падает в «Все категории». Селект выключен до `succeeded`.
2. Если загрузка списка упала, slug из URL всё равно используется как фильтр (`parseCategory` при `failed` оставляет значение). Селект при пустом `items` снова показывает «Все категории» и остаётся выключенным. Пользователь видит отфильтрованную таблицу, не может ни сменить категорию, ни понять, какая она. Остаётся только «Повторить» у предупреждения о категориях.

**Где.** `src/page/ProductFilters.tsx`, `categoryValue` около строк 42–45 и `disabled` около строки 69. Разбор при ошибке списка — `src/hooks/useProductsUrlState.ts`, `parseCategory` около строк 42–55.

**Что сделать.** Пока список не загружен, показывать slug из URL, а не «Все категории». При ошибке списка не блокировать селект целиком: оставить текущее значение, пункт «Все категории» и уже существующую кнопку «Повторить».

### DEF-004

| | |
|---|---|
| Статус | fixed |
| Серьёзность | minor |
| Область | таблица, ошибка |
| Требование | TC-103. Кнопка повтора есть, это про состав экрана во время ошибки |
| Связано | — |
| Исправление | 1 ноября 2026. `Alert` с повтором стоит над таблицей; прошлые строки и заголовки сортировки остаются |

**Симптом.** При ошибке списка пропадают таблица и заголовки сортировки. Остаются поиск, категория и alert.

**Как проверено.** Следующий запрос списка получил HTTP 500 с телом `Server exploded`. Экран показал этот текст и «Повторить», `table` в DOM не было. После восстановления сети «Повторить» загрузил сортировку по цене: первая строка Lemon, `0,79 $`. Пока ответ шёл, снова были видны старые строки. Это ожидаемо: `pending` список не очищает.

**Причина.** При `status === 'failed'` компонент возвращает один `Alert` вместо таблицы.

**Где.** `src/page/ProductTable.tsx`, ранний возврат около строк 82–95.

**Что сделать.** Оставить таблицу и показать alert над ней. Тогда во время ошибки можно сменить сортировку, а старые строки не исчезают из вида. Требование «ошибка с повтором» уже выполнено, это улучшение восстановления.

## Архитектурная оценка

Для одного экрана архитектура собрана правильно, и её ядро стоит сохранить.

Фильтры читаются из URL и в Redux не копируются. Из-за этого ссылка, новая вкладка, «Назад» и «Вперёд» работают без второй синхронизации. Черновик поиска при этом правильно остаётся в поле: в query уходит уже обрезанная строка через 300 мс.

Список и карточка разделены по типу и по запросу. Таблица просит `ProductListItem` с `select`, модалка — полный `Product`. Сливать их в один слайс «товар» не стоит.

Отмена устаревшего ответа сделана внимательно. `useLatestRequest` не рвёт запрос на cleanup эффекта, поэтому StrictMode не шлёт дубль. Это подтвердилось сетью.

Обход «поиск не умеет категорию» лежит в thunk, а не в таблице. Для костыля API это правильный слой. Ограничение самого обхода — [ARCH-010](#arch-010).

Стек менять не нужно. RTK рядом со второй библиотекой данных только усложнит экран. Выбрасывать RTK ради одной страницы тоже рано. Не нужно растить схему как «ещё один слайс на каждый запрос».

### Что сохраняем

- URL — единственный источник поиска, категории, сортировки и открытого товара.
- Локальный черновик поиска до debounce.
- Два типа и два запроса: список и карточка.
- Отмена предыдущего запроса и отсутствие лишнего запроса на старте.
- Фильтр категории при поиске внутри thunk, пока нет нового API.
- Форматирование и подписи в `src/page/format.ts`.
- MUI v9 без дополнительных UI-библиотек.

## Что менять не стоит

- Переезд на RTK Query или TanStack Query поверх уже написанного RTK. См. [ARCH-001](#arch-001).
- Пагинация «заодно». См. [LIM-003](#lim-003).
- Общий слайс товара для списка и модалки. Типы и запросы разные намеренно.
- i18n-фреймворк. См. [LIM-002](#lim-002).
- Нормализация «на вырост». См. [ARCH-002](#arch-002): текущую карту как раз стоит убрать, новую не заводить.
- Дублирование фильтров в Redux ради удобства компонентов.

## Замечания, которые дефектами не стали

- `aria-sort` стоит на `<th>`, а не на кнопке внутри. Для заголовка колонки это корректный ARIA. Кнопка сортировки есть. TC-208 засчитан.
- Нечисловой и неположительный `productId` снимается с URL. `productId=999` остаётся и показывает ошибку сервера. Падения нет, TC-305 засчитан.
- Лишнее имя параметра (`foo`) сохраняется. Это описано в [ARCH-009](#arch-009), не как порча известных фильтров.
- Вес в модалке выводится числом без единицы измерения. Требование просит показать вес, единица в нём не задана.
- Отдельное поле `thumbnail` в модалке не выведено. Обязательный список закрыт картинками `images`.
- Названия категорий с дефисом капитализируют только первую букву: «Mens shirts», «Home decoration». Это решение 13, TC-301 засчитан.

## Как проверялось

Браузер, приложение на `http://localhost:5173`, API `https://dummyjson.com`.

Отдельно от UI проверены ответы API: `limit=0` возвращает полный набор и сохраняет сортировку; плохая категория даёт пустой 200, а не 404; у части товаров нет `brand`; товар `999` отвечает 404 с `Product with id '999' not found`.

Сценарии в UI: первая загрузка и число запросов, сортировка по цене в три клика, приглушение старых строк, поиск с несколькими паузами, abort, «Назад» и «Вперёд», категория Smartphones, поиск Samsung внутри неё, модалка S10 со всеми блоками, Esc, фон, кнопка «Закрыть», Tab, Enter, пробел, фокус после закрытия, смена товара до прихода ответа, битый query, `productId=999`, ошибка 500 и «Повторить», ширина 390 px.

`npm run typecheck` и `npm run lint` на момент проверки проходят. Отдельного тестового раннера в проекте нет.
